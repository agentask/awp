# AWP-Sig v0.1 — Sync Signing Profile (RFC 9421 subset)

**Status:** draft. Normative for all sync calls to `hosted.endpoint` and their
responses. This subset **is** the spec: anything outside it MUST be rejected.
There is no negotiation and no algorithm agility.

## 1. Request signing

Exactly one signature per message, label `awp`.

```
Content-Digest: sha-256=:BASE64:
Signature-Input: awp=("@method" "@target-uri" "content-digest");created=1753088043;keyid="example.com/2026-07-01";alg="ed25519"
Signature: awp=:BASE64URL_ED25519:
```

### 1.1 Covered components — exact, ordered

1. `@method`
2. `@target-uri`
3. `content-digest` — present iff the request has a body (bodyless GET/HEAD
   omit both the header and the component).
4. Every `AWP-*` header present on the request (`awp-session`,
   `awp-delegation`), appended in lowercase alphabetical order.
   **An uncovered `AWP-*` header is a verification failure** — unsigned
   session or delegation material is worse than none.

### 1.2 Signature parameters

| Param | Rule |
|---|---|
| `created` | REQUIRED. Unix seconds. |
| `keyid` | REQUIRED. Format `{domain}/{kid}`, resolved via the domain index exactly as envelope signatures. The signing domain is the **caller's** — this is how a provider learns the caller principal for session binding. |
| `alg` | REQUIRED, `"ed25519"`, and MUST match the resolved key's declared alg (no header-driven agility). |
| `expires`, `nonce`, `tag` | MUST NOT appear. |

### 1.3 Headers

| Header | Content |
|---|---|
| `Content-Digest` | RFC 9530, `sha-256` only. REQUIRED on any request with a body. |
| `AWP-Session` | Provider session token (`state: provider` apps). |
| `AWP-Delegation` | base64url of the JSON delegation chain (core §2.5). |

## 2. Verification algorithm

Each step short-circuits on failure:

| # | Step | Failure |
|---|---|---|
| 1 | Parse `Signature-Input`. Reject unknown labels, missing/extra components vs §1.1, forbidden parameters. | `400` |
| 2 | abs(now − created) ≤ 300 s. | `401` |
| 3 | If body present: recompute `Content-Digest` (sha-256 only). **Digest before signature** — never verify a signature over a digest you haven't checked. | `400` |
| 4 | Resolve `keyid` (with core §0.1's one-refresh rotation retry). Unknown or revoked key. | `401` |
| 5 | Reconstruct the signature base (RFC 9421 §2.5); verify Ed25519. | `401` |
| 6 | If `AWP-Delegation` present: decode, verify per core §2.5; the chain's final delegate MUST equal the principal derived from `keyid`. | `403`, `code: unauthorized_delegation` |
| 7 | If `AWP-Session` present: token valid, unexpired, bound to the caller principal from `keyid`. | `401` |

## 3. Response signing

SHOULD sign; label `awp`; covered components `@status` and `content-digest`
(iff body); same parameter rules; `keyid` from the **provider's** domain.
Clients SHOULD verify. A present-but-invalid response signature MUST be
treated as an error — never fall back to unsigned trust.

## 4. Exclusions and rationale

| Excluded | Why |
|---|---|
| `nonce` | Idempotency lives at the envelope/application layer; a transport nonce adds server state for nothing. |
| `expires` | `created` + fixed 300 s window is one fewer knob to misconfigure. |
| Multiple signatures | No use case until relays exist (v0.2). |
| RSA / ECDSA | One algorithm, zero downgrade surface. |

## 5. Test vectors (to be generated by `awpd`'s conformance suite)

Each vector: fixed keypair, fixed request bytes, expected signature base,
expected `Signature` value. Minimum set: bodyless GET; POST with body; POST
with `AWP-Session`; POST with `AWP-Delegation` (2-link chain); each §2 failure
mode. Vectors live in `testdata/awp-sig/` and double as cross-implementation
conformance fixtures.
